# LINE 法務助理的框架與雲端部署研究計畫

更新日期：2026-11-03。

目前階段：已完成本輪 LINE API 與 Google 授權文件盤點、需求與驗收基準、13 個框架第一輪比較，以及雲端部署限制盤點。已提出原型驗證優先順序，實際帳號、原型、成本試算與最終選型尚未完成。

## 研究目標與範圍

為個人律師或法律事務所開發透過 LINE 互動的法務助理。助理協助管理案件、文件與客戶溝通，使用 Google Drive、Gmail 與 Google Calendar，保存長期記憶，並能定時處理工作與主動通知。

評估原始文章提到的全部 13 個選項，找出適合法務工作流程的框架與部署組合。每個選項都完成第一輪研究，再選出約三個候選深入驗證。不預設任何框架勝出。

部署限定雲端或託管服務，排除自家電腦與 NAS。比較完整組合，包括 Agent、LINE 入口、資料庫、文件儲存、背景工作、排程、授權與執行紀錄。

LINE Messaging API 是框架選型前的獨立研究項目。先確認平台限制與功能替代方式，再評估框架。初步官方查證記錄於 [LINE API 限制與驗證計畫](line-api-research.md)。

研究起點為 [給 Agent 開發者的駕馭工程第 9 篇](https://blog.aihao.tw/2026/06/26/harness-engineering-9-agent-frameworks/)。文章作為索引，框架能力與平台限制以研究當下的官方文件、原始碼與實測結果確認。

本文件記錄計畫，不代表已完成選型、驗證或部署。這次整理文件不會連接真實案件資料、發送客戶訊息或建立付費資源。

## 已確認的產品需求

文件、指令、資料夾與後續測試資料的示例統一使用 `範例客戶甲`、`範例律師甲` 這類名稱，不使用真實或看似真實的個人姓名。例如 `民事_範例客戶甲_侵權行為`。其他人員依序使用甲、乙、丙區分。

### 客戶群組

群組成員包含白名單中的律師、非白名單的客戶，以及法務助理。律師白名單與案件存取權限由程式檢查，不能由模型或訊息內容自行變更。

| 功能 | 預期行為 |
| --- | --- |
| 建立資料夾 | 使用 `民事_{客戶名字}_{案由}` 這類命名方式建立或連結案件資料夾。 |
| 接收與歸檔文件 | 接收群組文件、上傳至 Drive 並歸類，保存來源與處理結果。 |
| 定時掃描 Email | 找到新增或尚未處理的信件與附件，判斷所屬案件。 |
| 通知案件進度 | 將符合通知條件的進度發送至對應客戶群組。 |
| 知識庫問答 | 根據既有知識庫回答，附上資料來源。資料不足時轉交律師。 |
| 整理客戶訊息 | 彙整待律師處理的問題與附件，在固定時間提醒。 |

### 律師私人聊天室

| 指令或互動 | 預期行為 |
| --- | --- |
| `//檢查信件` | 統計並整理今天的信件內容。 |
| `//行事曆` | 詢問律師是否新增開庭行程，整理資訊後確認並建立。 |
| `//轉發信件` | 找到指定信件，確認案件與接收群組，轉發允許公開的內容。 |
| `//登記案號 民事 範例客戶甲 侵權行為` | 登記案件，建立或連結客戶、資料夾與群組。正式法院案號另設欄位。 |
| `//已登記案號` | 查詢已登記案件與正式案號。 |

保留使用者提供的指令作為需求範例。完整語法、補問方式與確認流程於設計階段決定。

Gmail 寄出新信件目前不列為已確認需求。將信件轉發至 LINE 群組屬於本次範圍。

## 必須釐清的系統能力

| 能力 | 研究問題 |
| --- | --- |
| 案件對應 | 如何連結律師、客戶、案件、正式案號、群組與 Drive 資料夾？同名客戶或多個案件如何區分？ |
| LINE 入口 | 獨立研究群組與帳號資格、身分辨識、歷史訊息、檔案收送、回覆時效、主動通知、計費、事件可靠性與收回訊息。詳見 [LINE API 研究](line-api-research.md)。 |
| Google 授權 | 使用個人帳號或 Workspace 時，如何處理 OAuth、權杖更新、撤銷、權限範圍與必要的審查？ |
| 文件處理 | PDF、掃描檔與其他附件如何讀取？何時需要 OCR？來源、版本與重複檔案如何保存？ |
| 案件辨識 | 如何結合正式案號、寄件人、信件往來與文件內容？無法確定或結果衝突時如何交給律師？ |
| 背景工作 | 定時掃信、事件通知、訊息彙整與提醒如何啟動？哪些適合固定排程，哪些適合事件觸發？ |
| 持久化執行 | 任務如何排隊、重試、取消，並在服務重啟後接續？等待律師確認時如何保存狀態？ |
| 避免重複操作 | 事件重送、API 逾時或程序中斷時，如何避免重複建資料夾、建活動與發通知？ |
| 記憶 | 如何分開保存對話、偏好、案件事實、待辦與排程？如何附來源、修正與刪除？ |
| 知識庫 | 如何匯入、檢索、引用與更新資料？如何處理資料不足、過期或互相矛盾？ |
| 權限與隔離 | 如何阻止客戶執行律師指令、跨案件讀取，以及信件或文件中的指令影響工具權限？ |
| 律師確認 | 哪些動作可自動執行？哪些需要確認？內部討論與可對客戶公開的內容如何區分？ |
| 維運 | 如何查看操作紀錄、追蹤錯誤、備份、恢復與監控未完成工作？ |

系統保存固定的案件識別碼、Drive 資料夾 ID 與 LINE 群組 ID。資料夾名稱可依需求調整，不作為唯一識別方式。

研究假設為先使用一個 Agent 配合明確的案件流程。是否加入子代理、Skills、Shell 或瀏覽器操作，由需求與驗證結果決定。

## 研究步驟與完成條件

### 前置研究：確認 LINE API 的可行範圍

查證 Messaging API 與一般 LINE App 的差異，分別記錄官方帳號資格、群組功能、訊息接收、檔案收送、主動通知與成本限制。不把一般 App 或官方帳號管理介面的功能視為 Messaging API 都能使用。

逐項將需求標為可直接實作、需要替代流程、需要帳號資格、待實測或不支援。初步已確認的限制與尚待查證項目分開保存。

完成條件為每個 LINE 相關需求都有可行方式或明確限制，列出測試步驟、帳號前提、成本影響與雲端元件需求。需要測試帳號才能確認的部分，明確標為待實測，不阻擋其他文件研究，但在縮小框架候選前處理會改變方案的限制。

這一步會決定文件改用受控連結的方式、訊息何時保存、長任務如何回覆，以及提醒無法送出時如何處理。框架評估以這份結果為共同前提。

### 第一階段：固定需求與驗收情境

整理角色權限、案件關係、資料流程與通知規則。把對話需求轉成可觀察的行為，分開標記已確認需求與研究假設。

產出需求表、待確認事項與共用驗證案例。每個核心需求都能對應至少一個案例，才進入第一輪比較。目前成果見 [需求與驗收基準](requirements-and-acceptance.md)。Google 授權與帳號差異見 [Google 整合研究](google-integration-research.md)。

### 第二階段：完成 13 個選項的官方資料研究

對每個選項使用同一份問題清單，查官方文件、原始碼、維護狀況、授權與部署說明。有疑點再查相關 issue，區分官方限制與個別回報。

每筆重要結論記錄來源連結、查證日期、適用版本與證據程度。證據程度分為文件確認、原始碼確認、實測確認與尚待確認。找不到資料不直接判定不支援。

產出完整比較表與每個選項的適用條件、缺口及補足方式。13 個選項都留下紀錄，不因熟悉度或使用中的開發工具而省略。

### 第三階段：比較框架與雲端部署組合

對照以下三類方向，先查硬性限制，再比較成本與工作量。

| 部署方向 | 必查項目 |
| --- | --- |
| 託管容器與背景工作服務 | 長任務、常駐程序、擴縮、排程、佇列、重啟與持久化儲存。 |
| Serverless 搭配佇列與排程 | 執行時限、程序啟動、狀態外存、等待確認與長任務接續。 |
| 託管 Agent 服務 | 框架相容性、工具權限、Google 授權、資料控制、遷移能力與平台費用。 |

每個可行組合列出 LINE 入口、Agent、背景工作、資料庫、排程、Google 授權與部署步驟。確認無人值守驗證方式，不把本機登入成功當成雲端可運作的證據。

比較 API 計費與訂閱登入的適用條件。費用包含模型、雲端運算、資料庫、儲存、OCR、檢索、LINE 訊息與監控。估算前先列使用量假設與查價日期，不用單一數字代表所有用量。

### 第四階段：縮小至約三個候選

先檢查雲端部署、案件隔離、Google 授權、等待確認、狀態恢復與主動通知能否合理實作。沒有內建能力時，評估補足方案的工作量與風險。

再比較可靠性、維護工作、開發速度、總成本、模型替換與遷移成本。評分權重在證據表完成後公開說明，不先用任意分數決定結論。

產出候選名單。每個未入選選項都說明原因與重新考慮的條件。約三個是控制驗證工作量的目標，候選數量可依實際差異調整。

### 第五階段：用相同案例驗證候選

先用合成案件、測試文件與模擬工具驗證。串接測試帳號時，把實際 API 行為與模擬結果分開記錄。各候選使用相同輸入、資料、工具契約與成功條件，記錄模型設定及無法公平對齊的差異。

先驗證案件登記、文件歸檔與群組通知，再加上訊息整理、Calendar、知識庫與記憶。

| 驗證情境 | 成功條件 |
| --- | --- |
| 登記案件與建立資料夾 | 案件、資料夾與群組連結正確，重複指令不建立重複資料。 |
| 新信與附件歸檔 | 找到正確案件並保留來源，不重複處理同一附件。 |
| 案件辨識不明確 | 不放入錯誤資料夾，不通知錯誤群組，保留待確認工作。 |
| 案件進度通知 | 僅傳送到登記群組，內容符合案件的通知規則。 |
| 客戶訊息定時彙整 | 包含待處理訊息與來源，已處理項目不反覆提醒。 |
| 建立開庭行程 | 整理時間、時區、法院與案件，經律師確認後建立，避免重複活動。 |
| 知識庫回答 | 引用正確來源，資料不足時不編造答案。 |
| 跨對話記憶 | 保存核准資訊與來源，修正或刪除後不再使用舊內容。 |
| 事件重送與重啟 | 不重複產生外部操作，未完成工作與待確認事項可恢復。 |
| API 逾時、限流或授權失效 | 顯示可追蹤的狀態，依規則重試或要求重新授權。 |
| 客戶越權與跨案件要求 | 不執行律師限定操作，不回傳其他案件資料。 |
| 文件含誤導 Agent 的指令 | 文件內容不改變角色、案件範圍或工具權限。 |
| LINE 群組已有其他官方帳號 | 明確指出平台限制，提供加入本助理所需的操作方式。 |
| 文字與附件保存 | 收到的文字及時保存，附件及時下載；無法取得時留下可處理的錯誤。 |
| PDF 轉發 | 使用有權限控制的文件連結，不把直接發送 PDF 附件列為 API 已支援功能。 |
| LINE 回覆與通知失敗 | 長任務不依賴長時間保留 reply token；封鎖、退群、額度不足與限流分開處理。 |
| 訊息編輯或收回 | 彙整、待辦與檢索不繼續使用失效內容，衍生資料依確認後的規則更新。 |
| 通知確認 | 區分 API 已接受與律師已確認，不以 HTTP 成功回應當作已讀證明。 |

記錄完成率、案件辨識錯誤、重複操作、恢復結果、回覆時間、模型用量、額外程式量與部署步驟。測量效能時說明測量條件與重複次數。原型缺陷與框架限制分開記錄。

### 第六階段：提出推薦與開發順序

產出首選與備選、完整雲端架構、費用組成、限制與尚未驗證事項。說明需求改變時，什麼條件下應改選其他組合。

列出第一版功能、驗收條件與後續開發順序。框架、資料庫、記憶、排程與背景工作各自的選擇都要有理由。

## 待確認事項與暫定處理方式

以下事項不阻擋第一輪文件研究。深入驗證或費用估算前，再確認相關假設。

| 待確認事項 | 暫定處理方式 |
| --- | --- |
| 律師、客戶與案件數量 | 起步服務個人律師，資料設計需能區分不同律師與案件，規模另確認。 |
| Google 個人帳號或 Workspace | 使用者已確認尚未決定，兩種都比較。 |
| 一個群組對應幾個案件 | 不預設一對一，保留明確的案件與群組關係。 |
| 白名單建立與維護 | 由律師管理，不從顯示名稱推論身分。 |
| 正式法院案號 | 與建立案件分開處理，可先登記案件再補案號。 |
| Email 來源與通知內容 | 支援定時掃信，發送範圍、信件來源與附件公開規則另確認。 |
| 自動處理與律師確認的界線 | 研究時先區分例行歸檔、例行通知與需要律師判斷的操作。 |
| 待處理訊息如何結案 | 評估標記完成、延後、交辦，以及提醒頻率。 |
| 知識庫位置、格式與適用法域 | 先記為未知，不預設法域或資料已完成整理。 |
| 檔案類型、大小與掃描比例 | 先查平台限制，OCR 工作量另估。 |
| 部署區域、預算與資料保存規則 | 比較可行組合，不先指定供應商或每月預算。 |
| 模型與開發語言偏好 | 先保持開放，選型時說明限制與替換方式。 |
| LINE 帳號地區、方案與認證資格 | 已有臺灣官方帳號，尚未設定 Messaging API。新版方案已查證，實際方案、資格與 Provider 待確認。 |
| 客戶群組是否已有官方帳號 | 先確認群組現況，再規劃機器人加入方式。 |
| LINE 歷史訊息與收回內容 | 不預設能補抓加入前紀錄，另確認歷史匯入與衍生資料處理需求。 |
